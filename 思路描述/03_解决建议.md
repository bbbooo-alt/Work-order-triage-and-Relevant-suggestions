# 第三步 · 解决建议（检索增强生成）

> 术语写法：英文原名（中文注解）。
> **前置**：第 1、2 步完成，分诊结果写入 `triage_results`（分诊结果）；`resolution_knowledge`（建议知识库）现有 3,032 条 `answer`（客服回复）向量，1,024 维。

## 0. 目标与最大短板

把「找回相似历史回复」升级为「检索资料 ＋ 生成可执行的解决建议」。**当前最大短板不是模型，是语料**：库里全是 `answer`，且多为「请提供日志／型号」的追问和安抚，**不是标准解决方案**，质量天花板很低。

## 1. 先补语料，再谈生成

- 引入权威知识：`SOP`（标准作业程序）、`FAQ`（常见问题）、产品手册、故障处理记录、已结工单的 `resolution`（解决方案）。
- 把 `body`（正文）也纳入索引可提升相似工单召回，但必须靠 `chunk_type`（分块类型）区分：`answer` / `body` / `kb`（知识库文档），检索时按类型加权。
- 全量灌入：`ITSM_EMBED_LIMIT=0 python scripts/embed_knowledge.py`（断点续灌）补齐 28,587 条；新增文档单独批量灌入。
- 每条保留来源与 `domain_id`（技能域编号），便于过滤和溯源。

## 2. 检索链路

1. **构造查询**：`subject`（标题）＋ `body` ＋ 阶段 2 的 `pred_type` / `pred_queue`（预测类型／部门）作为过滤条件。
2. **向量检索**：`HNSW`（向量近似检索索引）＋ `vector_cosine_ops`（余弦相似度算子）取 `top-k`（最相似的 k 条）。
3. **混合检索**（关键）：叠加关键词检索（`BM25` 或 PostgreSQL 全文检索 `tsvector`）——IT 工单里的型号、错误码、版本号是**强关键词**，纯向量容易漏。
4. **`rerank`（重排）**：对候选重新排序，再按 `domain_id` 过滤跨域噪声。
5. **拒答**：最高相似度低于阈值时，明确说「没有可靠依据」，不要硬编。

## 3. 生成

- `prompt`（提示词）中带上检索片段及其来源，要求「只基于给定资料、不确定就说明、给出排查步骤」。
- 输出结构化：建议步骤 / 需补充的信息 / 升级条件 / 引用来源。
- 用本地已有的 `qwen3:14b` 或 `deepseek-r1:7b` 即可，不必上云；中文输出让 `LLM`（大语言模型）直接生成，**不必先翻译语料**。

## 4. 评测（本步最难，因为无标准答案）

| 侧 | 指标 | 做法 |
|---|---|---|
| 检索 | `Recall@k`（前 k 条命中相关资料的比例）、`MRR`（平均倒数排名） | 建 50~100 条 `golden set`（黄金评测集：人工标注「哪些资料算相关」） |
| 生成 | 相关性、可执行性、是否有幻觉 | 人工评分 ＋ `LLM-as-judge`（用大模型当评审），但必须用人工抽样校准评审口径 |

**取舍**：先做「只检索不生成」——把相似历史回复和知识片段展示给工程师，确认有用再上生成；否则无法判断问题出在检索还是生成。

## 5. 格外注意的坑与标准解法

| 坑 | 标准解法 |
|---|---|
| 语料质量差、全是追问 | 引入权威 `kb` 文档、去重、标明来源与类型 |
| 幻觉（编造不存在的步骤） | 只基于检索片段、强制引用、低相似度拒答 |
| 分块过大／过小 | 按语义分块（约 300~600 字符 ＋ 重叠），保留标题路径 |
| 型号／错误码被向量漏掉 | 混合检索（向量 ＋ 关键词）＋ `rerank` |
| 维度超限 | `pgvector`（向量扩展）的 `HNSW` 上限 2,000 维，用 `Matryoshka`（套娃表示）截断到 1,024 维 |
| 没有客观指标就宣布「效果不错」 | 先建 `golden set`，人工评分 ＋ `LLM-as-judge` 校准 |
| 把 `answer` 当标准答案 | 明确它只是**回复风格参考**，不是解决方案 |

混合检索 ＋ 重排 ＋ 引用溯源是 `RAG`（检索增强生成）的成熟标准做法；`Recall@k`／`MRR` 是检索侧的标准指标。

## 6. 产物与脚本

- `scripts/index_knowledge.py`：灌入知识文档与全量工单文本。
- `scripts/suggest.py`：检索 ＋（可选）生成，输出结构化建议。
- `eval/golden_set.csv`（人工标注评测集）、`reports/rag_eval.md`（检索与生成评分）。

## 7. 完成判据

1. 全量工单与权威文档已入索引，`chunk_type` 可区分来源。
2. `Recall@k` 达到预设线，混合检索相对纯向量有提升。
3. 人工评分通过（无严重幻觉、建议可执行），拒答机制可用。
4. 「只检索」与「检索＋生成」两套结果做过对比，明确各自适用场景。

> 一句话原则：**先补语料，再做检索，最后才生成；没有 `golden set` 就不要评价效果好坏。**

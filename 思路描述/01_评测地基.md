# 第一步 · 评测地基

> 术语写法：英文原名（中文注解）。
> **目标**：在写任何模型之前，先把「怎么算好坏」固化下来，并跑通一个最笨的 `baseline`（基线，作为对照底线）。原话：「固定 `train/val/test`（训练/验证/测试划分），先定指标——分类与优先级看 `macro-F1`（宏平均 F1，各类别等权），路由看派单成功率、超时率、负荷均衡；再跑一个最笨的基线（关键词规则 ＋ 轮询派单）。没有基线就不上模型。」

## 0. 这一步解决什么

模型好坏无法判断时，任何改动都只是猜。本步产出**一把固定的尺子**：冻结的测试集、统一评测脚本、可追溯的基线分数。完成后才进入阶段 2（分诊模型）。

## 1. 冻结数据划分

- **现状**：`tickets`（工单主表）已有 `split`（数据集划分），按 `queue × priority × language`（部门 × 优先级 × 语种）分层，`train/val/test` = 22,871 / 2,858 / 2,858；`body`（正文）28,587 条全唯一，已无重复行。
- **要做**：把 `ticket_id → split` 导出为冻结清单 `eval/split_frozen.csv`，之后脚本**只读不写**；校验无同一工单跨划分、三层比例符合 80/10/10。
- **铁律**：调参只用 `train`（训练集）、选模型用 `val`（验证集），`test`（测试集）最终只评一次；不得重切、不得在 `test` 上挑阈值或挑提示词。
- **风险**：按行随机切会让重复/近似重复文本跨集泄漏；本步已去重，但仍要检查近重复（正文高度相似的不同工单）。

## 2. 指标体系

| 任务 | 主指标 | 辅助指标 |
|---|---|---|
| 分类 `type`（工单类型，4 类） | `macro-F1`（宏平均 F1） | `per-class F1`（逐类 F1）、`accuracy`（准确率）、混淆矩阵（confusion matrix） |
| 分类 `queue`（处理部门，10 类） | `macro-F1` | 同上 |
| 优先级 `priority`（3 档） | `macro-F1` | 相邻错误率、`MAE`（平均绝对误差，把 low/medium/high 映射为 0/1/2） |
| 路由到工程师 | 派单成功率、超时率、负荷均衡 | 平均派单耗时、无可用工程师比例 |

- **为什么用 `macro-F1`**：`Change`（变更）仅约 10%、`low`（低优先级）约 21%，`accuracy` 会掩盖少数类崩塌。
- **优先级是有序类别**：把 `high` 判成 `low` 比判成 `medium` 严重得多，所以补相邻错误率与 `MAE`，不能只看分类对错。
- **负荷均衡**：各工程师派单数的标准差或 `Gini`（基尼系数），越小越均衡。
- 解决建议（`RAG` 检索增强生成）本步**不评**，留到阶段 3 用检索命中率 ＋ 人工评分。

## 3. 路由怎么离线评（本步最难）

- `assignments`（派单记录）目前为空，没有真实派单流，因此用 `test` 集按 `created_at`（创建时间）排序做**离线回放**（`replay`，按时间顺序模拟工单陆续到达）。
- 每条工单求可选工程师集合：`engineer_skills`（工程师技能表）∩ `required_skills[]`（所需技能）＋ `shifts`（排班表）在岗 ＋ 未超 `engineers.capacity`（并发上限）。
- **必须隔离**：评测产生的派单要写进独立表 `eval_assignments`，或给 `reason`（派单原因）加 `EVAL:` 前缀；计算 `current_load`（当前负荷）时排除评测数据，否则基线会污染线上负荷。
- 超时判定：`decided_at`（派单时间）/ `closed_at`（结单时间）与 `sla_due`（处理时限）比较。

## 4. 基线（对照组）设计

| 组件 | 最笨做法 | 作用 |
|---|---|---|
| 绝对下限 | `most-frequent class`（多数类，永远预测最常见的类） | 判断任何模型是否真的学到了东西 |
| `type` / `queue` 分类 | 关键词规则（英／德双语词表，如 outage→Incident、billing→Billing and Payments） | 语义模型之前的对照 |
| `priority` 判定 | 关键词规则（urgent / outage / security→high，其余 medium） | 同上 |
| 路由 | `round-robin`（轮询，轮流分配，**不看**技能／班次／负荷） | 用来证明「约束求解」确实带来收益 |

- 全部预测写 `triage_results`（分诊结果），`model_version`（模型版本）标 `baseline-v0`，`tickets` 里的真值（人工标注的标准答案）**一律不动**。
- 基线越笨越好，它只负责给出下限；后续模型必须显著超过它，且不能靠牺牲少数类换总分。

## 5. 产物与脚本

- `scripts/run_baseline.py`：生成基线预测与离线回放派单，写入 `triage_results` / `eval_assignments`。
- `scripts/evaluate.py`：统一评测，输入 `model_version`，输出所有指标；任何后续模型**必须复用同一脚本**，保证可比。
- `eval/split_frozen.csv`：冻结划分清单。
- `reports/baseline_metrics.json` ＋ 混淆矩阵 CSV：可追溯的基线分数。
- 固定随机种子（`seed`），保证一键重跑得到相同数字。

## 6. 格外注意的坑与标准解法

| 坑 | 标准解法 |
|---|---|
| 数据泄漏（重复/近重复跨集、在 `test` 上挑阈值） | 去重后再分组划分（`GroupShuffleSplit` 分组划分）＋ 冻结清单，测试集只评一次 |
| 类别不均衡只看 `accuracy` | `stratification`（分层抽样）＋ `macro-F1` ＋ 混淆矩阵，逐类看召回 |
| 优先级有序性被忽略 | 追加相邻错误率与 `MAE`（平均绝对误差） |
| 评测派单污染 `current_load` | 独立表 / `EVAL:` 标记，负荷统计时排除；派单要在事务内完成并用 `SELECT ... FOR UPDATE`（行锁）避免并发超派 |
| 基线太弱造成「虚高提升」 | 同时给出多数类底线与关键词规则基线两条对照 |
| 合成数据 ＋ 造数的工程师/排班 | 结论只能说明「流程跑通」，**不能当生产预期**；上线前走 `shadow mode`（影子模式，只记录不生效）＋ 人工抽检 |

指标计算本身有成熟实现：`scikit-learn` 的 `classification_report`（分类报告）可直接给 `macro-F1` 与逐类指标；离线回放与影子模式是调度／推荐系统的标准评测方式。

## 7. 完成判据（满足才进阶段 2）

1. 评测脚本一键重跑，同一 `test` 集产出相同指标（确定性）。
2. 三类任务指标全部成表，且包含逐类 `F1` 与混淆矩阵。
3. 基线分数落盘并可追溯（`model_version` ＋ 时间戳），`assignments` 未被污染。
4. 预先写死进阶门槛，例如 `macro-F1` 相对基线提升 ≥ 3 个点、无任一类别 `F1` 下降，路由成功率不低于基线且负荷更均衡。

> 一句话原则：**尺子先于模型，基线先于优化，测试集只许看一次。**

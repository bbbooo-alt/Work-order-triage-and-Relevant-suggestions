# 第四步 · 路由到工程师

> 术语写法：英文原名（中文注解）。
> **前置**：第 1 步的离线回放框架与轮询基线、第 2 步的 `triage_results`（分诊结果）已就绪。
> **现状**：`engineers`（工程师表）12 人、`engineer_skills`（技能表）27 条、`shifts`（排班表）42 条**均为造数**；`assignments`（派单记录）为空。

## 0. 目标

按**排班规则、工程师技能、工程师负荷**把工单派给具体工程师，结果写 `assignments`，并让每个决策可解释、可复盘。

## 1. 决策链：硬约束 → 软打分 → 落库

- **输入**：`pred_queue` / `pred_type` / `pred_priority`（阶段 2 预测）、`tickets.required_skills[]`（所需技能）、`created_at`（创建时间）。
- **硬约束**（三条缺一不可，不可违背）：
  1. 技能匹配：`engineer_skills ∩ required_skills[]` 有交集；
  2. 班次在岗：`shifts` 覆盖该时刻（注意 `on_call` 值班与时区）；
  3. 负荷未满：`current_load`（当前负荷）< `engineers.capacity`（并发上限），且 `active`（在用）。
- **软打分**：`proficiency`（熟练度）、`level`（等级）、当前负荷（越空越优）、高优先级优先给高 `level`；后期可加历史同类工单处理表现。
- **输出**：`assignments` 的 `engineer_id`、`load_at_assign`（派单时在手工单数）、`reason`（命中规则与扣分明细）。

## 2. 算法取舍

| 方案 | 适用 | 建议 |
|---|---|---|
| 逐条贪心（按时间顺序，每条选当前最优） | 工单陆续到达、量小 | **先做这个**：简单、可解释、好调试 |
| 批量最优（`assignment problem` 指派问题，匈牙利算法 Hungarian / 最小成本流） | 同一时刻积压多单、追求全局最优 | 高峰期再上，作为二期优化 |
| `LLM`（大语言模型）直接派单 | — | **不用**：不可复现、无法审计、出问题难追责 |

标准解法是「硬约束过滤 ＋ 成本最小化」，本质属于运筹学的指派问题；冷启动用加权打分 ＋ 硬过滤已足够。

## 3. 并发与一致性（本步最关键）

- `current_load` **不存静态字段**：在事务内用 `SELECT ... FOR UPDATE`（行锁）锁定工程师行，或对 `assignments` 中「待处理／已接」实时聚合计数。
- **派单幂等**：同一 `ticket_id`（工单编号）只能有一条有效派单，靠唯一约束或「先查后写」保证，避免重复点击造成双派。
- 记录 `load_at_assign` 与 `reason`，事后可完整复盘「为什么派给他」。

## 4. 边界情况（必须提前定义）

- **无可用工程师**（技能／班次／负荷全不满足）→ 转人工队列、升级或排队，**绝不能硬派**。
- 高优先级工单抢占、跨时区夜班 `on_call`（值班）。
- 班次切换时在途工单的归属（`closed_at` 结单时间跨班次）。
- 评测回放数据必须与线上隔离：`eval_assignments`（独立表）或 `EVAL:` 前缀，负荷统计时排除（第 1 步已定）。

## 5. 评测（复用第 1 步的离线回放）

| 指标 | 含义 |
|---|---|
| 派单成功率 | 满足全部硬约束且成功派出的比例 |
| 超时率 | `decided_at` / `closed_at` 超出 `sla_due`（处理时限）的比例 |
| 负荷均衡 | 各工程师派单数的标准差或 `Gini`（基尼系数），越小越均衡 |
| 无可用工程师比例 | 边界情况发生频率 |

必须与第 4 节的轮询 `baseline`（基线）对比，证明约束求解确实带来收益。

## 6. 格外注意的坑与标准解法

| 坑 | 标准解法 |
|---|---|
| 静态负荷字段导致并发超派 | 事务 ＋ 行锁 ＋ 实时聚合计数；派单幂等 |
| 只看技能不看班次／负荷 | 三段硬约束缺一不可 |
| 大模型拍脑袋派单 | 规则引擎 ＋ `audit log`（审计日志）＋ `reason` |
| 造数的工程师/排班分布不真实 | 结论只说明「流程跑通」；接真实排班后走 `shadow mode`（影子模式）再校准 |
| 无可用工程师未处理 | 明确降级路径（人工／升级／排队） |
| 离线回放污染 `current_load` | 独立表或 `EVAL:` 标记，统计时排除 |

## 7. 产物与脚本

- `scripts/route.py`：硬约束过滤 ＋ 打分 ＋ 事务内写 `assignments`。
- `reports/routing_metrics.json`：四项指标及与轮询基线的对比。
- `assignments` 中每条都带 `load_at_assign` 与 `reason`，可追溯。

## 8. 完成判据

1. 派单成功率、超时率、负荷均衡三项均优于轮询基线，且无任一工程师超 `capacity`。
2. 边界情况有明确降级路径，无硬派、无双派。
3. 并发场景下负荷计算正确（可加锁压测验证）。
4. 每条决策可通过 `reason` 复盘，才进入阶段 5。

> 一句话原则：**硬约束不可妥协，负荷实时算，决策必须能解释；不用大模型拍板派单。**

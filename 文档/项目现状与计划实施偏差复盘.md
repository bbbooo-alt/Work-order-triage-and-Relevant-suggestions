# 工单分诊与解决建议 · 现状总结与「计划 → 实施」偏差复盘

> 日期：2026-11-09
> 对比基线：`项目实施思路.md`、`思路描述/01~05_*.md`、`数据库设计说明.md`（规划阶段）
> 事实依据：`reports/*.json` 五份实测报告、`scripts/*.py` 与 `web/*.html` 实际代码、五套验收页的 `run_all` 返回值（实施阶段）
> 判定标签：`一致`（按计划落地）／`等价替换`（做法不同但目标等价）／`缩减递延`（计划内明确留到二期，或本轮主动收窄）／`未达成`（完成判据没满足）／`计划外新增`（规划里完全没有）

## 0. 一页速览

五个阶段全部实现并各自通过独立验收，**流程打通、指标可复现、评测隔离干净**；但与规划相比不是「照单执行」，而是出现了明显偏移。三条最需要被记住的结论：

1. **两条链路没有打通**：第二步的 `pred_skills`（预测所需技能）始终为空，第四步只能拿工单真值标签当路由输入；第三步的生成环节完全没做，只做到「只检索不生成」。规划文档把这两处写成主线，实施里变成了断点。
2. **两处完成判据被实测推翻，处理方式比计划更保守**：混合检索在隔离评测集上没有超过纯向量，系统用「上线护栏」自动降级；约束路由的负荷均衡（`load_std` 5.1）明显劣于轮询基线（0.47），改用「合法派单数 / 合规率 / 超时率」重新定义胜负，而不是硬凑三项全优。
3. **规划里完全没有「验收方式」这一层**：用户要求只通过前端点点点验收、每步页面不能混用，于是多出 5 套独立端口、独立页面、独立报告、独立启动脚本，以及一整套「前序报告哈希前后对比」的隔离校验。这部分是纯增量，也反过来约束了后续所有写库行为（线上 `assignments` 必须保持 0 行）。

**总评**：本轮交付的是一套**可复现的离线验证系统**，不是可上线系统。`cc-by-nc-4.0` 禁止商用、工程师/排班为造数、知识库仅 12 条英文文档、测试集被反复用于只读演练，这些都使指标只能说明「流程跑通」。

## 2. 计划 vs 实施：逐步骤偏差

### 2.1 第一步 · 评测地基

| 规划项 | 实施结果 | 判定 | 说明 |
|---|---|---|---|
| 冻结 `train/val/test`，导出 `split_frozen.csv`，之后只读 | `freeze_split.py` 提供 `run()` / `check()`，28587 行校验通过 | 一致 | |
| 校验三层比例 80/10/10、无跨集重复 | 校验唯一 `ticket_id`、合法 `split`、同一 `body` 不跨划分、`train` 比例落在 0.75~0.85 | 等价替换 | 严格 80/10/10 改成区间；「重复」按**正文完全相等**判断，近重复未查 |
| 指标体系：`macro-F1` + 逐类 `F1` + `accuracy` + 混淆矩阵；`MAE` + 相邻错误率 | 全部落在 `baseline_metrics.json`；额外加 `severe_error_rate`（high 判成 low） | 一致 | 但混淆矩阵只在 JSON 内，**没有规划里写的独立 CSV** |
| 路由指标：派单成功率、超时率、负荷均衡（标准差或 `Gini`）、平均派单耗时、无可用工程师比例 | 实做 `valid_rate` / `timeout_rate` / `load_std`；`Gini`、平均耗时、无可用工程师比例未做 | 缩减递延 | 后两项在第四步才以 `degraded_rate` 形式补上 |
| 离线回放按 `created_at` 排序，超时与 `sla_due` 比较 | 抽样 500 条，时间按 `md5` 排序后线性映射到排班窗口 80% 区间；超时用硬编码 `SLA_HOURS = {high:4, medium:24, low:72}`，**未读 `tickets.sla_due`** | 等价替换 | 造数没有可信 `sla_due`，但真实 SLA 口径因此未打通 |
| 基线写入 `triage_results`，`model_version` 标 `baseline-v0` | 标为 `majority-v0` / `keyword-v0` 两条 | 等价替换 | 命名不同，但两条对照比规划的单条更符合「别让基线太弱造成虚高」 |
| 评测派单写独立表 `eval_assignments` | 实做；后续又扩展出 `route_assignments` 等隔离表 | 一致 | |
| 预先写死进阶门槛 | `eval/thresholds.json`：`+0.03`、无类别下降、路由合规 `0.90`、超时 `0.20`、`test` 只评一次 | 一致 | 第二步与第四步的验收确实自动读取并判定这些门槛 |
| 固定 `seed`、一键重跑确定性 | `random_state=42`；第一步页面连续跑两次评测比对全字段一致 | 一致 | |
| — | 独立验收页 8765、11 项检查、`.bat` 自愈启动 | 计划外新增 | 用户新增的验收方式要求 |

**小结**：第一步是五步里偏差最小的，`尺子先于模型` 的原则被完整保留。主要缺口是 `sla_due` 口径、近重复检查、`Gini` 与混淆矩阵 CSV。

### 2.2 第二步 · 分诊

| 规划项 | 实施结果 | 判定 | 说明 |
|---|---|---|---|
| L1 `embedding` + 线性分类头（`LogisticRegression` / 线性 SVM） | `TF-IDF`（`char_wb` 3–5 元语法，`max_features=30000`）+ `SGDClassifier(loss="log_loss")` | 等价替换 | 明确理由：冷启动不依赖 Ollama、秒级可重跑。但**不是 embedding**，规划里「复用 `qwen3-embedding:4b`」未落地 |
| L1 → 与 L2（`few-shot`/`LLM`）对比 → 视收益决定 L3（微调） | 只做到 L1 | 缩减递延 | 规划把 L2/L3 列为建议顺序，本轮未做，也未给出「不上 L2」的量化依据 |
| 输出 `pred_skills[]`（预测所需技能） | 恒为 `{}` | **未达成** | 最关键的链路断点：第四步的硬约束只能用 `tickets.required_skills` 真值，等于离线回放的上界 |
| 低置信度转人工，保留「不确定」出口 | 阈值 `0.45`，`test` 中 112 条被标记 | 部分达成 | 只做了标记，没有工单状态流转、人工队列或处置动作 |
| `priority` 推荐方案 B：`ITIL` `impact × urgency` 矩阵 | 仍是普通三分类 + `MAE` + 严重错误率（方案 A 的一半） | 缩减递延 | `tickets.impact / urgency` 字段未参与建模，也没能直接对齐 `SLA` |
| 按 `language` 分层评测，英德不掉点 | 实做 `en`/`de` 三任务 `macro-F1`，并纳入检查项 | 一致 | |
| 类别权重 + `stratification`，`macro-F1` 为主 | `val` 在 `plain` / `balanced` 两配置中选出 `balanced`；`macro-F1` 为主 | 一致 | |
| 标签噪声：抽检 200~300 条 + `confident learning` | 未做 | 缩减递延 | `queue` 的 `macro-F1` 仅 `0.428`，噪声很可能是主要天花板，但没有证据定位 |
| 中文 / 多语言嵌入 | 未做（语料本身只有 en/de） | 计划内递延 | |
| 产物 `train_triage.py` + `predict_triage.py` | 合并为单个 `triage.py` | 等价替换 | |
| 完成判据：三任务 ≥ 基线 +3 点、无类别 `F1` 下降、`MAE` 不劣化、英德不掉点 | `build_checks` 逐项自动判定，16/16 通过 | 一致 | 这是唯一一步**完成判据被逐条自动校验**的阶段 |

**小结**：指标提升非常大且合规，但实现路径换成了更轻的词面模型，规划里「embedding → L2 → L3」的技术递进、ITIL 优先级矩阵、技能预测三条主线没有落地。

### 2.3 第三步 · 解决建议

| 规划项 | 实施结果 | 判定 | 说明 |
|---|---|---|---|
| 目标：检索资料 + **生成**可执行建议 | 只做到「只检索不生成」，返回原文片段与来源 | **缩减** | 规划第 4 节自己写了「先做只检索不生成」的取舍，但第 0 节目标与第 7 节完成判据仍要求生成，属于规划内部不一致 + 实施取了保守侧 |
| 补权威语料：`SOP`/`FAQ`/产品手册/已结工单 `resolution` | 12 条英文 KB 文档（按 12 个技能域各写一份排查步骤），均为人工概括而非真实文档 | 等价替换 | 语料短板被正视了，但「权威」是团队自撰，不是业务正式文档 |
| 全量灌入 28,587 条 `body`（`ITSM_EMBED_LIMIT=0`） | 确定性抽样 800 条 | 缩减递延 | 出于嵌入耗时考虑；检查项据此改为 `>=800` |
| 按语义分块（300~600 字符 + 重叠）、保留标题路径 | 每条 KB 一整段、工单正文截前 2000 字符，无重叠、无标题路径 | **未达成** | |
| 查询构造带 `pred_type` / `pred_queue` 过滤；按 `domain_id` 过滤跨域噪声 | 查询只用纯文本；`domain_id` 只用于事后判定相关性 | 缩减递延 | |
| 混合检索：向量 + `BM25`/`tsvector` | `HNSW` 向量 + `GIN`（物化 `fts` 生成列）全文检索 + 分层分桶 `RRF` 融合 | 一致 | 额外做了「权威 kb 单独成桶」，避免被 3,832 条历史片段淹没 |
| `rerank`（重排） | 只是 `RRF` 加权重排，不是 `cross-encoder` 重排 | 等价替换 | |
| 拒答：最高相似度低于阈值 | 实测相似度无法区分相关/无关，改用「词面重合数 `>=1`」+ 极低相似度兜底 | 等价替换 | 依据充分：正负样本分布重叠（见 3.2） |
| 50~100 条**人工标注** `golden set` | 50 条**弱标注**：以工单首个技能域对应的 KB 文档为相关文档 | **未达成** | 报告里已如实标 `weak_label`，但指标因此有「同义反复」风险 |
| 生成侧人工评分 + `LLM-as-judge`；「只检索」与「检索+生成」两套对比 | 均未做 | **未达成** | |
| `Recall@k` 达预设线且**混合检索相对纯向量有提升** | 验证集选出权重 `0.3`（`MRR 0.6333 → 0.7083`），但隔离评测子集出现回退，护栏自动降级为纯向量 `0.0` | **未达成** | 处理方式正确（不硬凑），但完成判据字面没满足 |
| 产物 `index_knowledge.py` / `suggest.py` / `reports/rag_eval.md` | `knowledge.py`（索引 + 建议 + 评测一体）、`reports/rag_metrics.json` | 等价替换 | |
| — | 20/30 调参与评测子集隔离、4 档权重择优、上线护栏、拒答校准实验、独立验收页 8767 | 计划外新增 | 全部源于实测中暴露的问题 |

**小结**：第三步偏差最大。规划把它当「RAG 生成」阶段，实施实际交付的是「可评测的混合检索 + 保守拒答」阶段，生成链路整段缺失。

### 2.5 第五步 · 上线闭环

| 规划项 | 实施结果 | 判定 | 说明 |
|---|---|---|---|
| 三档逐档放开；自动档**仅高 `confidence` + 低风险**生效 | 三档 + 回退开关；自动档门禁只有 `kill_switch`，**没有置信度/风险准入条件** | **缩减** | 112 条低置信度工单没有真正被自动档排除 |
| `human_override` 与 `triage_results` / `assignments` 逐条对比形成可训练标注 | `feedback_events` 记录改判；只按 `split` 分流到标注池 | 缩减递延 | 没有逐条字段级 diff，也没有真正触发重训 |
| `active learning` 优先标注最不确定样本 | 未做 | 缩减递延 | 标注池 3 条，无排序逻辑 |
| 回流只进 `train`，`test` 永不改动 | 实做：`test` 泄漏 0 条，冻结划分仍 2,858 行 | 一致 | |
| 监控：数据侧（drift/语种/低置信度）、效果侧（`macro-F1`/超时率/降级率/改判率/拒答率）、工程侧（检索命中率/派单重试/`current_load` 异常） | 4 个指标（低置信度率、拒答率、降级率、改判率）+ 2 条快照（含注入的漂移探针） | 缩减递延 | 语种分布、在线 `macro-F1`、检索命中率、重试、负荷异常均未接 |
| 每次变更记录 `model_version`、配置、评测分数、生效时间 | 未做版本注册表，只有各阶段自己的报告与 `decision_log` 的 `mode` | 缩减递延 | |
| 合规：许可证、造数边界、`PII` 脱敏、访问控制、审计日志 | 许可证与造数结论写入报告；脱敏 + `decision_log` 审计实做；**访问控制未做** | 部分达成 | |
| 影子跑满一个完整业务周期、人工抽检通过、差异可归因、`A/B` 测试 | 36 张冻结 `test` 工单的只读演练；无真实流量、无周期、无抽检、无 A/B | **未达成** | 报告已列入已知限制 |
| 告警规则、回退开关演练 | 4 个写死阈值 + 注入探针验证告警触发；开关打开后自动模式被拒并回退 `shadow` | 一致 | |
| 产物 `shadow_run.py`、反馈表、`reports/online_metrics.md`、监控看板 | `lifecycle.py` + 5 张表 + `lifecycle_metrics.json` + 前端交互面板 | 等价替换 | 没有独立 md 报告与看板，能力集中在验收页 |
| — | 沙盒 `auto_assignments`、漂移探针注入、模式状态持久化、独立验收页 8769 | 计划外新增 | |

**小结**：闭环的「控制面」（模式、门禁、回退、审计、告警）搭起来了，但「数据面」和「时间面」（真实流量、业务周期、回流→重训）没有打通。

## 3. 实施阶段暴露、规划阶段未考虑到的问题

### 3.1 检索与评测方法（规划里最盲区）

| # | 问题 | 实测表现 | 当时的处理 | 是否彻底解决 |
|---|---|---|---|---|
| 1 | 嵌入相似度**绝对值**不可用于拒答（各向异性） | 相关工单 KB 最高相似度 `0.3814~0.6882`，无关查询 `0.3552~0.6061`，分布重叠；`top1 − 中位数` 间隔同样重叠 | 拒答改用「查询实词与 KB 文档的词面重合数 `>=1`」，相似度只留 `0.30` 兜底 | 否：德文工单与英文 KB 词面重合低，拒答率 `0.4667`（纯向量）/ `0.2667`（混合）偏高 |
| 2 | 长工单直接喂 `plainto_tsquery`（AND 语义）**零命中** | 首批 5 个查询 `keyword_hits` 全为 0，混合检索退化为纯向量 | 实词抽取 + 停用词过滤 + 前缀 OR `to_tsquery`，并建物化 `fts` 生成列承载 `GIN` | 部分：OR 查询命中面过宽，仍需 reranker 才能提精度 |
| 3 | 权威文档被海量历史片段淹没 | 3,832 条 `answer`/`body` 与 12 条 `kb` 同池排序，`kb` 进不了 top5 | 分层分桶召回：kb 单独一桶，各桶独立 `RRF` 排名 | 是（就本轮指标而言） |
| 4 | 关键词权重在验证集有效、在隔离评测集回退 | 验证子集 `0.3` 权重把 `MRR 0.6333 → 0.7083`；护栏触发前的中间运行里，holdout 上 `Recall@5 0.9333 → 0.8667`、`MRR 0.6706 → 0.6650`（最终报告是护栏降级后的 `0.9333 / 0.6706`） | 新增「上线护栏」：出现回退只降级为纯向量，绝不拿评测集反向挑权重；并把 golden set 拆成 20 调参 / 30 评测 | 部分：20/30 样本太小，结论本身不稳定 |
| 5 | 弱标注 golden set 有「同义反复」风险 | 相关文档定义为「工单首个技能域对应的 KB」，检索又用同一技能域体系 | 报告标 `weak_label` 并写入已知限制 | 否：需要人工标注才能证伪 |
| 6 | 轮询基线的「均衡」与「合法」不可兼得 | 基线 `load_std 0.47` 但合法派单仅 46/500；约束路由 `load_std 5.10` | 重新定义比较口径：合法派单数、合规率、超时率、最大负荷/容量 | 是（口径层面），但规划完成判据字面被推翻 |
| 7 | 事后复盘历史派单会把「未来」的派单算进当时负荷 | 首次交互演练 8 张工单全部显示「无可用工程师」，与真实回放状态全不一致 | 负荷查询按 `assignment_id < 当前单` 截断；未参与回放的工单用空回放版本 | 是（8/8 复盘一致） |

### 4.3 第三步 · 解决建议

| 问题 | 为什么重要 | 建议动作 | 优先级 |
|---|---|---|---|
| 生成环节整段缺失 | 规划的第 0 节目标与完成判据未满足，项目名里的「解决建议」目前只是「相关片段列表」 | 用本地 `qwen3:14b` 基于检索片段生成结构化建议（步骤 / 需补信息 / 升级条件 / 引用 `chunk_id`），并做「只检索 vs 检索+生成」对比 | **最高** |

| 生成侧无评分、无幻觉检查 | 一旦上生成，无法判断是否有编造 | 人工评分表 + `LLM-as-judge`，用人工抽样校准评审口径 | 高 |

| 20/30 的调参/评测样本太小 | 权重择优结论不稳定（验证集选 `0.3`、评测集回退） | 扩到 200+ 条并做交叉验证，或直接用固定保守权重 | 中 |
| `answer` 仍作为候选且未降权 | 规划明确「它只是回复风格参考，不是解决方案」 | 给 `answer` 更低权重或仅在 `kb` 全不命中时兜底 | 中 |
| 护栏把关键词权重降为 0，「混合检索」名存实亡 | 功能存在但默认关闭，容易被误读为已完成混合检索 | 页面与报告已如实写明；后续需用更大样本重新验证是否该开启 | 中 |

### 4.5 第五步 · 上线闭环

| 问题 | 为什么重要 | 建议动作 | 优先级 |
|---|---|---|---|
| 自动档门禁没有「高置信度 + 低风险」条件 | 规划明确要求；现在只靠 `kill_switch` 一刀切，112 条低置信度工单不会被自动档排除 | 用第二步校准后的置信度 + 优先级/类型风险分级做准入，并统计自动档覆盖率 | **最高** |
| 「回流 → 重训」闭环没有打通 | 标注池只有 3 条且从未被消费，完成判据第 2 条未满足 | 建训练样本导出 + 新版本评测 + 与冻结基线对比的流水线（只从 `train` 取数） | **最高** |
| 没有真实流量、没跑满业务周期、没有人工抽检、没有 A/B | 完成判据第 1 条未满足，影子模式的价值没被验证 | 明确一个观察周期与抽检抽样方案，再谈放量 | 高 |
| 漂移阈值 `0.40/0.60/0.70/0.35` 是拍脑袋写的 | 当前窗口本来就因 `human_override_rate 0.5` 告警，阈值缺乏分布依据 | 用影子期历史分布定分位数阈值，区分「告警」与「自动回退」两级 | 高 |
| 监控维度不全 | 缺语种占比、在线 `macro-F1`、检索命中率、派单重试、`current_load` 异常 | 按规划第 3 节三类补齐，并给每条规则配处置人/动作 | 中 |
| 告警只在验收页显示 | 没有通知渠道与处置流程 | 接邮件/IM 或至少落 `alert_events` 表 + 处置状态 | 中 |
| `human_override` 没有逐条字段级 diff | 无法形成可训练标注 | 记录 `field / old / new / actor / 时间 / 原因`，与 `triage_results`、`route_assignments` 关联 | 中 |
| 无版本注册表 | 「重训后无法复现历史结论」的坑仍在 | 建 `model_registry`（版本、配置、数据指纹、评测分数、生效/回滚时间） | 中 |
| 访问控制/权限未做 | 合规第 4 节只做了一半 | 至少给 `feedback_events` / `decision_log` 加角色与最小权限 | 中 |
| 真实 `assignments` 仍为空 | 自动档写的是沙盒表，上线链路没真正接通 | 定义「何时允许写线上表」的开关与回滚事务，并在影子期结束后演练 | 高 |
| 合规只有结论文字 | `cc-by-nc-4.0` 禁止商用是硬约束 | 在数据入口加许可证校验/标记，生产替换数据源前禁止切换到自动模式 | 中 |

## 5. 跨阶段的结构性缺口

| 缺口 | 涉及阶段 | 说明 |
|---|---|---|
| 技能预测断点 | 二 → 四 | `pred_skills` 为空，路由只能用真值标签，整条链路不能上线 |
| 生成断点 | 三 → 五 | 只检索不生成，第五步的 `decision_log` 里「检索」阶段只记录 `abstain` 与 top1，没有建议文本可供人工抽检 |
| 真实数据/排班断点 | 一 / 四 / 五 | 覆盖率、负荷、漂移阈值都建立在造数上，指标不能当生产预期 |
| `test` 口径风险 | 一 → 三/四/五 | 只读演练反复使用冻结测试集，靠约定而非技术强制保证「只评一次」 |
| 表结构与文档脱节 | 全局 | 设计说明仍写「8 张表」、`ticket_id NOT NULL`、无 `fts` 列；实际多了 7 张表 + 1 列 + 1 处约束变更 |
| 门槛覆盖不全 | 一 → 三/五 | `thresholds.json` 只被二、四步自动读取；三、五步没有预设量化门槛 |
| 验收体系本身未纳入规划 | 全局 | 5 套前端 + 哈希隔离校验是纯增量，但它反过来决定了「哪些表不能写」，需要在设计说明里正式记录 |
